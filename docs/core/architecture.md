# Hatchlane architecture

**Implementation baseline · 22 November 2026 · One customer, one Linux VM, simulated equipment**

Build one TypeScript application. Next.js serves the React interface, Hono handles the HTTP API inside the same Node.js process, and Better Auth handles local sign-in and sessions. PostgreSQL owns the operational record. Serve the field phone and desk browser from the same HTTPS origin. Package the app, database and Caddy reverse proxy with Docker Compose. A site can run the full permit workflow over its LAN with internet access disconnected. The product plan defines lifecycle and delivery scope. The design system defines screen behavior. [Product plan](product-plan.md) · [Design system](design-system.md)

## What runs where

| Location | Responsibility |
|---|---|
| Phone or desk browser | Next.js renders the initial permit, list or drawing shell on the server. React Client Components handle drawing pins, camera scanning, form edits, attendance and polling. Keep unfinished input visibly separate from acknowledged changes. |
| VM · Caddy | Terminate HTTPS on the site hostname. Reverse-proxy to the Next.js app over the private Compose network. The app image contains its own matching static assets. Only the proxy publishes an application port, 443 on the site LAN. |
| VM · Next.js + Hono | Run one standalone Node.js server. Next.js owns pages and Hono owns the same-origin API under `/api`. Both use server-only TypeScript modules for site permissions and workflow transactions. The simulation-labelled controller screen submits explicit local decisions. |
| VM · PostgreSQL | Own the current state, permit history, local accounts, database sessions, drawing revisions, attachments and simulator state. Only the app and local maintenance processes can connect. |
| VM · host timers | Run a short idempotent expiry sweep using the deployed app image and a nightly backup using PostgreSQL’s tools. Log the last successful run. Request-time validity checks remain authoritative between sweeps. |

Use an internal DNS name and a certificate trusted by field devices. Prefer the site's certificate when available. For a demonstration, Caddy’s local issuer works after its public root has been trusted on each device. Serve fonts, scripts, the PDF worker and its resources locally. Validate scan, GPS, asset lookup and permit submission on the actual site Wi-Fi with external DNS and internet unavailable. [Caddy internal HTTPS](https://caddyserver.com/docs/automatic-https#local-https)

## Why this architecture fits the job

| Decision | Trade-off and point to revisit |
|---|---|
| Use one web application | Keep page rendering, login and API commands in one deployment. Hono gives the simulator and field UI a shared command interface. Only split the API into its own service if a future client or gateway needs an independent release cycle. |
| Use PostgreSQL from slice one | Two reviewers can approve competing permits, or a person can be recorded entering just as a supervisor starts closeout. Row locks and database constraints make those outcomes testable. The same engine runs in development, concurrency tests and the VM. |
| Start with polling | Explorer needs to notice a fault on another asset while detail stays open. Poll one small authorized site-summary endpoint every two seconds while visible, immediately after a write and on regain of focus. Poll the active job at the same cadence or include it in the response. Back off on failure and label last contact. Twenty visible clients at two seconds produce about 10 requests/s per endpoint. Measure that load before introducing SSE, WebSockets or Redis. |
| Store bounded attachments in PostgreSQL | One database transaction commits the revision, evidence and original bytes. One consistent backup restores all three. The cost is larger WAL, dumps and restores. Measure daily attachment growth and restore time before moving immutable blobs to a filesystem or object store. |
| Keep simulation in the application | Explicit local decisions, independent sensor events, denial, delay and disconnect can be exercised without a broker. Add a gateway process and select a protocol when a bench controller and its interface are known. Hardware actuation and protective functions need a separate engineering decision. |
| Ship a Compose bundle | Three pinned services can be rehearsed and replaced together on one VM. The VM remains a single failure domain. Native services would also work, but require coordinating host Node.js, PostgreSQL and proxy upgrades at each site. |

## Application and data boundaries

Mount `new Hono().basePath('/api')` in `app/api/[[...route]]/route.ts`. Use the Node.js runtime and export the supported HTTP methods with `handle(app)` from `@hono/vercel`. Put HTTP handlers under `server/api/`, authorized reads and commands under `server/domain/`, and the pool and SQL access under `server/db/`. A Server Component can call an authorized read directly. Browser mutations go through Hono. Render protected pages per request and return `Cache-Control: private, no-store` for protected API responses and downloads. Keep authenticated data out of shared caches and clear the client workspace on sign-out. Public content-hashed JS, CSS and fonts can be cached long term. [Hono on Next.js](https://hono.dev/docs/getting-started/nextjs) · [Next.js backend guide](https://nextjs.org/docs/app/guides/backend-for-frontend)

Organize workflow code around four areas. The web app, simulator inputs and scheduled commands share these operations.

- **Site and equipment.** Make printed asset IDs unique within a site and serials unique among current assignments. Give each asset one gateway slot and one device slot per named layer. Store the assignment generation with commissioning acceptance. Reference each pin by asset, immutable drawing revision and page. Save coordinates from 0 to 1 measured from the top left of the unrotated visible page and transform them through the PDF viewport at display and placement. Keep old pins on their original revisions until the Admin confirms the new pin. Store optional GPS with accuracy and capture time independently. Asset labels encode a site-scoped asset route. Device labels encode a typed serial identifier. Decode both locally and resolve them within the signed-in site.
- **Permits.** Store the editable draft, immutable submitted versions and checklist snapshot, named duty holders, review decision, window and asset reservation. Store UTC instants and the site's IANA time zone. Reject nonexistent local times and require an explicit offset for repeated local times. Each resubmission creates a new immutable version. Keep stop reason and reconciliation holds independent of the lifecycle state. Search permit history by asset and number.
- **Field work.** Store timed evidence, ventilation sessions, decisions tied to evidence and permit version, release intents, local results, four independent signal projections, entrant visits, discrepancies and closeout confirmations. Give entrants stable permit-scoped IDs to distinguish identical names. Preserve event and server receipt times. Record an attestation with the authenticated actor, scope and server time.
- **History.** Append events with actor or equipment identity, site, permit/asset, action, correlation ID and original event reference for corrections. Commit the event and state change together. Preserve immutable audit order and display by event time with recording time and stable tie-breaking. Deduplicate source events. Polls and unchanged heartbeats leave history intact. Preserve the observations used as evidence for a decision even when their values match earlier samples.

The desktop and phone use the same command handlers. Every write checks the current actor and assigned duty, loads the current record version, and validates the transition on the server. Keep operational tables out of generic administrative edit screens.

Expose a site summary with reservations, layer signals and alerts, plus permit detail with the current version, server time, validity deadlines, authorized actions, next owner and blocking reasons. Provide typed commands for lifecycle changes, evidence, releases, movement, closeout and commissioning. Use explicit command outcomes for business conflicts and field errors, including the current version or blocker where authorized. Publish an operation lookup scoped to the original actor and target so a client can resolve an uncertain response without repeating a command. Never read or write a record using a bare client-provided ID without checking site and access.

### Accounts, sessions and permissions

1. **Sign in locally.** Mount Better Auth at `/api/auth/*` in Hono and use its PostgreSQL adapter. Enable email/password sign-in and set `emailAndPassword.disableSignUp`. Use the email address as the login identifier. Provision accounts directly so sign-in and recovery work without an external identity provider or mail service. Configure the public HTTPS site URL and trusted origin at runtime. Keep Better Auth's origin and CSRF checks enabled. Use secure HTTP-only cookies and rate-limit sign-in attempts. Store the Better Auth secret in a permission-restricted runtime file and trust proxy headers only from Caddy. [Hono integration](https://www.better-auth.com/docs/integrations/hono) · [Email and password](https://www.better-auth.com/docs/authentication/email-password) · [PostgreSQL adapter](https://www.better-auth.com/docs/adapters/postgresql)
2. **Provision and recover named accounts.** Use a one-shot VM command to create the first Admin after migrations through the Better Auth Admin plugin's server-side API. Read the initial password from a protected prompt or secret file. Keep the same VM-only path available to provision a named recovery Admin if all Admins lose access. Expose account creation, password reset and account disablement through guarded Hatchlane admin actions that call the plugin with the authenticated Admin's session. Allow only the required Better Auth paths and HTTP methods at the browser-facing mount. Disable accounts while retaining their user IDs and recorded decisions. Record who performed each account action without logging credentials or session tokens. [Better Auth Admin plugin](https://www.better-auth.com/docs/plugins/admin)
3. **Check permissions on every request.** Map Better Auth's `admin` and `user` roles to Hatchlane's Admin and Operator. Store site membership, duty eligibility and facilitator permission by Better Auth user ID. A Site Admin manages their site's members, assets and reviews. The assigned operator owns drafts and field checks, the assigned supervisor owns authorization and final certification, and the assigned attendant owns attendance and reconciliation. Grant simulator commands only to the site's facilitator. The facilitator who acknowledges a request must be a different actor from its requester. The simulator read exposes only equipment and command context. Hono and Next.js resolve current account status and permissions for pages, APIs and downloads. Keep session cookie caching disabled. Enforce the exact HTTPS origin and accepted content type on Hatchlane browser mutations. [Better Auth session management](https://www.better-auth.com/docs/concepts/session-management)

Hatchlane stores an account gate with reset-in-progress and must-change-password states. Route sign-in, Admin reset and forced change through the application so credential updates and session issuance for one account are serialized across requests. Before setting a temporary password, block access and sign-in for that account. Set the password and revoke all sessions using the server-side Admin APIs, then require a password change before protected requests. Leave an interrupted reset blocked and allow a Site Admin to retry it. After a successful forced change, clear the flag and revoke other sessions. Account provisioning exposes access only after creating the membership and password gate. Allow the account's password change and sign-out while the force-change gate is set. Verify account and duty status again for protected writes inside the command transaction.

On session expiry, prompt for sign-in and return the user to the same permit after checking access again. Reload its current state. Resolve any uncertain write by operation ID and require a fresh user action for any release or entry authorization.

## Simulation policy and timing

Ship one seedable, versioned checklist and demo policy. Its sample readings and classifications are synthetic fixtures. Seed valid, missing, expired and adverse scenarios explicitly. Keep numeric readings and display units in the record. Derive demo guard outcomes from the selected scenario, instrument checks and timing, without interpreting demo numbers as site operating limits.

| Stage | Required demo evidence |
|---|---|
| Pre-opening | Physical label confirmation, attestations for isolation, PPE, communications and rescue readiness, emergency contact, and a complete pre-opening observation. |
| Authorization | Current assessment observation for oxygen, flammability, H₂S and CO with the fields in the product plan. Instrument calibration and bump check must be confirmed. Record ventilation operation for the planned demo period, or use the checklist's explicit **Inapplicable** option with a reason. Record the supervisor's decision against the current version and evidence. |
| Monitoring | Keep a complete current assessment or monitoring observation after authorization. A valid later sample renews the current deadline when it arrives before lapse. The prior pre-opening sample remains evidence of that completed check. A missing or adverse required result, an invalidating correction, an unresolved alarm or a lapse after authorization stops work. A delayed record stays in history and cannot restore a stopped permit. |
| Closeout | Attendant's roster reconciliation and all-out confirmation, both layers confirmed secured, and operator checks for site cleanup and return-to-service before the supervisor signs. |

Use demo defaults of a 5-minute sample validity window, 120-second signal freshness, 30-second release timeout, 15-second controller lease and 30-second attendant lease. Renew each connection lease every five seconds while its workflow is active. The facilitator can publish fresh readings of unchanged simulated positions. A lease heartbeat is a separate event type. Calculate validity from observation time. Record rejected future timestamps and out-of-order events without promoting them to current evidence. Store deadlines in UTC, use server time after acquiring workflow locks, and enforce deadlines at equality. Use an injectable test clock for expiration cases. Run the idempotent sweep approximately every 15 seconds to materialize stop and expiry events. Reads and commands enforce validity immediately, including between sweeps.

## Workflow rules that must survive a race or restart

| Operation | Transaction rule |
|---|---|
| Review, reserve and start | Lock the asset before the permit. Check the immutable submitted version, reviewer outside the job team and current duty eligibility. Only approval claims the unique asset reservation. Check commissioning, window, alarms and asset holds as specified in the product lifecycle. Start requires the assigned operator, physical label confirmation and an open window. Reject stale decisions and simultaneous approval attempts with the current blocker. |
| Request and fulfil release | Tie the intent to the caller, permit version, target assignment, reason, deadline, controller session and operation ID. Recheck permit, actor, window, evidence, alarms, reconciliation and required fresh positions under the asset lock at request and fulfilment. Require at most one unresolved request per layer. Acknowledgement belongs to the request. Count its opening feedback only from that layer's current assignment and session, observed after acknowledgement. An acknowledged request with incomplete feedback remains unresolved. Following denial or timeout, require fresh secured feedback from both signals on the target after the outcome and a deliberate new action. |
| Disconnect, stop or expire | Each asset's simulator lease has a session ID. Disconnect or lease lapse ends pending intents. Reconnect starts a fresh session and requires new signal observations. Invalidate prior sessions once at app startup before accepting requests. One-shot maintenance commands leave the generation intact. Never replay intents. Invalidate any pending intents and entry authorization on stop, withdrawal or expiry, retaining their prior outcomes. Write a single event per invalidation. Keep the VM clock synchronized with a site time source. Send deadlines in protected reads so browsers can mark data stale even when a poll fails. |
| Record movement | Serialize on the same asset and permit locks. Enforce one open visit per entrant with a partial unique constraint. Planned entry rechecks eligibility, the attendant lease, authorization, both layer pairs and the acknowledged inner request. Preserve actual movement reports with stable identities, including unmatched exits and unexpected entrants as discrepancies. Clear the all-out confirmation on subsequent observed entry. An out-of-order or unmatched report requires reconciliation before it changes existing visits. |
| Close, cancel or hand off | Closeout cancels pending intents and blocks planned entry. Before releasing the reservation, verify a current reconciled empty roster and attestations, the inner-first closeout confirmation and four fresh secured signals from current assignments. Invalidate final attestations when their referenced checks change. Verified unused cancellation requires fresh secured signals and no start, request, movement or unresolved occupancy. Retain the reservation if any check fails. Recovery duty changes require a reason, current eligibility and a stopped job. Record the new actor separately from the immutable approved duty. |
| Recommission or record a late report | During a stopped job, accept equipment replacement only after the attendant's all-out confirmation. Preserve old assignments and require four new observations and commissioning acceptance before closeout. A movement racing closure either blocks closure or appends a discrepancy to the terminal permit. A late report with unresolved occupancy sets an asset-wide reconciliation hold and stops any active job without changing its roster or reservation. The Site Admin arranges an eligible attendant to reconcile actual movements on the affected asset and records the resolution with fresh feedback before clearing the hold. Expiry, restart and recovery cannot issue a relock. |

Activate the attendant's separate lease when they take responsibility on the permit. Require it for inner release and planned entry. After inner acknowledgement or while attendance is in progress, an interruption or lease lapse sets a reconciliation hold under the asset lock, even if the recorded roster is empty. Block new releases, planned entry and final closeout during the hold. Keep exits and actual movement reports available. The attendant signs the reconciled roster to clear the permit hold. On recovery, authenticate again if needed, reload current state and resolve uncertain writes by operation ID. Operational writes require deliberate online action.

Use a stable client operation ID across uncertain responses. Authenticate and authorize first. In one transaction, a repeated ID with the same actor, target and payload returns its recorded outcome. A mismatch or stale form returns a conflict with current state. Give each source event an identity and each signal a source sequence. Advance a signal only for the current assignment and session, a higher sequence for that signal and a valid observation time at least as recent as its last accepted value. Treat contradictory readings for the same source position or incompatible current bolt and layer values as a conflict on the affected layer until fresh, coherent feedback resolves it. Preserve late events and conflicts in history. A new session or heartbeat cannot freshen a reading. Store current state and reservations in PostgreSQL. For each transaction use one checked-out pool client, lock actor access where it changes and then lock the asset, permit and dependent rows in that order. Commit the change and event together. Roll back on error and release the client. Use two independent clients in concurrency tests. [node-postgres transaction guide](https://node-postgres.com/features/transactions)

## Disk, volumes and recovery

**Starting budget.** For the two-manhole simulation, allocate 2 vCPU, 4 GiB RAM, 24 GiB for the OS/images and 32 GiB of persistent SSD for PostgreSQL. These are starting estimates. Measure PDF upload memory, concurrent polling, peak WAL and restore time with representative drawings. Keep device heartbeat timestamps in current state. Log health transitions and significant evidence. Never silently prune permit history to reclaim disk.

| Data | Placement and recovery |
|---|---|
| Database including attachments | Mount an explicitly provisioned data disk at `/srv/hatchlane/data`. Bind its `postgres` directory to **`/var/lib/postgresql`** inside the official 19 image. Its default data directory is `/var/lib/postgresql/19/docker`. Require the host mount and expected disk identity before Compose starts, including after VM reboot. Disable automatic host-directory creation for this bind. On this dedicated VM make the Docker daemon depend on the verified UUID-backed mount so automatic container restarts cannot bypass it. After first provisioning, check for the expected cluster before launch and fail closed on an empty or wrong disk. Test a reboot with the disk detached. [Container restart behavior](https://docs.docker.com/engine/containers/start-containers-automatically/) · [Official image volume layout](https://hub.docker.com/_/postgres) |
| Certificates, credentials and configuration | Keep Compose manifest, release digest list and Caddyfile with the release. Protect mounted secrets separately. Persist Caddy’s `/data` and `/config` across recreation. If using its local CA, keep an encrypted recovery copy of CA material and limit access. Replacing the root requires retrusting phones. |
| Temporary files, logs and images | Put upload staging on the OS disk with bounded space. Cap and rotate container logs. Retain the active and previous release images. Monitor OS and database space and inodes separately. Keep backup output on its designated destination so it cannot fill the database volume. |

**Attachment policy.** Use one raw file body per authenticated drawing revision or asset photo upload, with the parent in the URL and server-generated attachment and revision IDs. Submit pin placement and GPS independently as JSON. Set the Caddy request cap to 20 MiB for uploads and use smaller route-specific caps elsewhere. In Hono, authenticate before reading the stream and count incoming bytes even without a Content-Length header. Cap PDFs at 20 MiB and JPEG/PNG photos at 5 MiB. Check actual type, file signature and readable content. Reject drawings requiring a password and bound PDF render canvas size and concurrent uploads. Remove temporary staging files on success, abort or failure. In one transaction, commit the revision or photo association and bytes, size and SHA-256. Ordinary permit/list queries load metadata only. Fetch files from an authenticated endpoint with fixed content type and no shared cache. Render drawings with the bundled PDF worker, with document scripting disabled. Bundle a representative multi-page drawing in slice 1. Exercise upload limits, including a streamed body without a Content-Length header, through the packaged proxy in slice 5. [Caddy request limits](https://caddyserver.com/docs/caddyfile/directives/request_body) · [PostgreSQL binary data](https://www.postgresql.org/docs/19/datatype-binary.html)

**Capacity check.** Twenty jobs/day × two 2 MiB photos × 90 days is about **7 GiB** of new payload before drawings, indexes, row history, WAL and backups. Ninety days is a sizing example, not a deletion policy. Sample actual growth weekly. Start space alerts at 75% and 85%, stop accepting optional uploads when headroom is low, and preserve space for roster and closeout writes. If the database cannot commit, report the write as unconfirmed and reconcile from site records after recovery. Expand the disk or move attachments when forecast headroom or restore time misses the agreed target.

**Backup and restore.** Use a host timer to stream a nightly custom-format `pg_dump` from the matching database image to an encrypted, customer-controlled destination on separate storage. All application services remain on the VM. A second disk on the same VM alone cannot recover loss of the host. Budget separate destination capacity for seven retained full dumps plus one in progress and headroom, using measured dump size. Publish a completed backup only after checking the exit status, archive readability and hash. Then rotate older copies. Record success time and release ID, and alert if the last verified copy exceeds 24 hours. Recreate DB roles/grants from a protected bootstrap manifest, and recover secrets, TLS and release images alongside the database. Demo targets are at most 24 hours of database loss and a two-hour recovery, subject to a timed drill. [PostgreSQL logical backups](https://www.postgresql.org/docs/19/backup-dump.html)

Restore into an empty database on an isolated VM or Compose project using the archived release. Verify schema, permit and event counts, attachment hashes, reservations and roster against a backup manifest from the same transaction snapshot. Export a snapshot for both the manifest queries and pg_dump and keep its transaction open through the dump. Before exposing the restored workspace, invalidate pending intents, authorization and sessions, mark observations stale and set an asset-wide recovery hold. Treat any restored started job as stopped and preserve its reservation. Allow reconciliation, evidence recording and closeout during recovery. An older backup can omit an entire job, so the Site Admin verifies account changes and records reconciliation and fresh feedback for **every asset**, including unreserved assets, before clearing the recovery hold and enabling new work. Record the recovery and elapsed time. [PostgreSQL snapshot option](https://www.postgresql.org/docs/19/app-pgdump.html)

## Delivery and verification

Build Next.js from an ESM package with `output: 'standalone'` in a multi-stage image. Copy `.next/standalone`, `.next/static` and `public` into the final layout, and launch the generated `server.js` with Node. Copy compiled maintenance entrypoints, their runtime dependencies, SQL migrations and the migration runner into the release as well. Next.js tracing starts at the web entrypoints and can omit files used only by a CLI. Inject database credentials, the Better Auth secret and trusted site URL at runtime. Use a restricted application DB role and a separate migration owner. Build with a local font source and package vendor assets so the VM needs no network downloads. [Next.js standalone packaging](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)

Ship prebuilt app, proxy and database images, their digests, the Compose manifest and one-shot Node commands for migrations, bootstrap and expiry. The VM can load the bundle from customer media. Bootstrap named accounts, the checklist and both sample assets explicitly on a new simulation instance. Schedule upgrades between jobs. Verify the disk mount, drain active requests, stop application writes and expiry jobs, then take and verify the cutover backup. Run migrations once and start healthy services in maintenance mode. Allow sign-in and reads for smoke checks through Caddy while operational writes and timers are paused. Before enabling those writes, use the previous image for schema-compatible rollback or restore the matching pre-upgrade backup for incompatible migrations. Expose an app readiness check for DB/schema availability and show the last successful backup to the Site Admin.
